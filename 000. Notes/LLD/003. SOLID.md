# SOLID Design Principles (Part 1)
*Based on the video by Coder Army*

## 📌 Introduction to SOLID Principles
When working on real-world projects with thousands of classes, tightly coupled and messy code can lead to disastrous bugs. Maintaining such architecture is difficult, reading the code becomes tough for new engineers, and introducing new features becomes a nightmare. 

To solve this, **Robert C. Martin** (Uncle Bob) introduced the **SOLID** design principles in the year 2000. SOLID is an acronym that stands for:
1. **S** - Single Responsibility Principle (SRP)
2. **O** - Open/Closed Principle (OCP)
3. **L** - Liskov Substitution Principle (LSP)
4. **I** - Interface Segregation Principle (ISP)
5. **D** - Dependency Inversion Principle (DIP) 

---

## 1️⃣ Single Responsibility Principle (SRP)
**Definition:** *A class should have only one reason to change, meaning it should only have one responsibility or do one thing.*

If a class handles multiple responsibilities (e.g., calculating price, saving to a database, and printing invoices), changing the logic for one responsibility will force you to modify the class, which might inadvertently break the other functionalities. 

### Bad Example (Violating SRP)
A `ShoppingCart` class that calculates totals, prints invoices, and saves to the database.

```java
// VIOLATES SRP
class ShoppingCart {
    private List<Product> products = new ArrayList<>();

    public void addProduct(Product p) { products.add(p); }
    
    // Responsibility 1: Logic
    public double calculateTotalPrice() { /* ... */ return 0.0; }
    
    // Responsibility 2: Presentation
    public void printInvoice() { /* ... */ }
    
    // Responsibility 3: Persistence
    public void saveToDatabase() { /* ... */ }
}
```

### Good Example (Following SRP)
Split the responsibilities into different classes using **Composition**. 

```java
// FOLLOWS SRP

// Class 1: Handles only cart logic
class ShoppingCart {
    private List<Product> products = new ArrayList<>();
    public void addProduct(Product p) { products.add(p); }
    public double calculateTotalPrice() { /* ... */ return 0.0; }
}

// Class 2: Handles only printing
class ShoppingCartPrinter {
    private ShoppingCart cart;
    public ShoppingCartPrinter(ShoppingCart cart) { this.cart = cart; }
    public void printInvoice() { /* Print logic using cart... */ }
}

// Class 3: Handles only database persistence
class ShoppingCartStorage {
    private ShoppingCart cart;
    public ShoppingCartStorage(ShoppingCart cart) { this.cart = cart; }
    public void saveToDatabase() { /* DB logic using cart... */ }
}
```

## 2️⃣ Open/Closed Principle (OCP)
**Definition:** *A class should be open for extension but closed for modification.*

When adding a new feature, you should not modify existing, tested code. Instead, you should extend the functionality (using Abstraction, Interfaces, and Polymorphism).

### Bad Example (Violating OCP)
Adding MongoDB and File storage support by modifying the existing storage class with `if-else` or new hardcoded methods.

```java
// VIOLATES OCP
class ShoppingCartStorage {
    public void saveToSql() { /* ... */ }
    
    // Modifying existing class to add new features!
    public void saveToMongoDb() { /* ... */ }
    public void saveToFile() { /* ... */ }
}
```

### Good Example (Following OCP)
Use an Interface/Abstract class. Create specific concrete classes for each new feature.

```java
// FOLLOWS OCP
interface DBPersistence {
    void save(ShoppingCart cart);
}

class SqlPersistence implements DBPersistence {
    @Override
    public void save(ShoppingCart cart) { /* SQL save logic */ }
}

class MongoDbPersistence implements DBPersistence {
    @Override
    public void save(ShoppingCart cart) { /* MongoDB save logic */ }
}

// If Cassandra DB is needed tomorrow, just create a new class. No existing code is touched!
class CassandraPersistence implements DBPersistence {
    @Override
    public void save(ShoppingCart cart) { /* Cassandra logic */ }
}
```

## 3️⃣ Liskov Substitution Principle (LSP)
**Definition:** *Subclasses should be substitutable for their base classes.*

If a client expects a Parent class, you should be able to pass a Child class without breaking the application or causing unexpected behavior (like unhandled exceptions). The child class must extend the parent's capability, not narrow it down.

### Bad Example (Violating LSP)
A `FixedDepositAccount` inheriting from `Account` but throwing an exception for `withdraw()` because FDs don't allow withdrawals. 

```java
// VIOLATES LSP
abstract class Account {
    abstract void deposit(double amount);
    abstract void withdraw(double amount);
}

class SavingsAccount extends Account {
    void deposit(double amount) { /* ... */ }
    void withdraw(double amount) { /* ... */ }
}

class FixedDepositAccount extends Account {
    void deposit(double amount) { /* ... */ }
    
    // Narrows down parent capability and causes unexpected errors for the client!
    void withdraw(double amount) { 
        throw new UnsupportedOperationException("Cannot withdraw from FD"); 
    }
}
```

### Good Example (Following LSP)
Refactor the hierarchy. Group classes by their actual supported behaviors using segmented interfaces.

```java
// FOLLOWS LSP
interface DepositOnlyAccount {
    void deposit(double amount);
}

interface WithdrawableAccount extends DepositOnlyAccount {
    void withdraw(double amount);
}

// Savings Account supports both
class SavingsAccount implements WithdrawableAccount {
    public void deposit(double amount) { /* ... */ }
    public void withdraw(double amount) { /* ... */ }
}

// Fixed Deposit ONLY implements DepositOnlyAccount
class FixedDepositAccount implements DepositOnlyAccount {
    public void deposit(double amount) { /* ... */ }
    // No withdraw method forced upon this class anymore!
}
```
Now, the client maintains separate lists for `DepositOnlyAccount` and `WithdrawableAccount`. The client code won't accidentally call `withdraw()` on a Fixed Deposit account, ensuring LSP and OCP are perfectly maintained.


## 📌 Deep Dive into Liskov Substitution Principle (LSP) Guidelines
Strict guidelines to identify if a child class is truly substitutable for its parent class (LSP). The guidelines are divided into three rules:

### 1. Signature Rule
*   **Method Argument Rule:** The arguments of the overridden method in the child class must be exactly the same or a *broader* (parent) type than the arguments in the parent class method. (Note: Strongly typed languages like Java enforce exact matching for method overriding anyway).
*   **Return Type Rule (Covariance):** The return type of the overridden method in the child class must be exactly the same or a *narrower* (child) type of the return type in the parent class.
*   **Exception Rule:** The overridden method in the child class can only throw the same exception or a *narrower* (subclass) exception as the parent class method. It cannot throw a *broader* (parent) exception or a completely unrelated exception.

### 2. Property Rule
*   **Class Invariant:** A rule or fact that must always remain true for a class. If the parent class has an invariant (e.g., `balance >= 0`), the child class must respect it and cannot weaken it (e.g., a child `CheatAccount` cannot allow negative balances).
*   **History Constraint:** The history or fundamental state behavior of a parent class must not be modified by a child class. (e.g., if a parent class dictates that `withdraw()` is always an allowed behavior, a child class like `FixedDepositAccount` cannot block `withdraw()` by throwing an exception). Also, child classes cannot make an immutable property of a parent class mutable.

### 3. Method Rule
*   **Pre-condition:** A condition that must be met *before* a method executes. A child class can apply the exact same pre-condition or make it *weaker* (more lenient), but it cannot make it *stricter*.
*   **Post-condition:** A condition that must be met *after* a method executes. A child class can apply the exact same post-condition or make it *stricter* (adding more guarantees), but it cannot make it *weaker*.

## 4️⃣ Interface Segregation Principle (ISP)
**Definition:** *Many client-specific interfaces are better than one general-purpose interface. Clients should not be forced to implement methods they do not need.*

Instead of creating a massive, "fat" interface with many methods, you should segregate (split) it into smaller, highly cohesive interfaces.

### Bad Example (Violating ISP)
A general `Shape` interface forces 2D shapes to implement a `volume()` method they don't possess.

```java
// VIOLATES ISP
interface Shape {
    double area();
    double volume();
}

class Square implements Shape {
    public double area() { return side * side; }
    
    // Forced to implement a method it doesn't need!
    public double volume() {
        throw new UnsupportedOperationException("2D shapes don't have volume");
    }
}

class Cube implements Shape {
    public double area() { /* ... */ return 0.0; }
    public double volume() { /* ... */ return 0.0; }
}
```

### Good Example (Following ISP)
Segregate the interface into 2D and 3D shapes.

```java
// FOLLOWS ISP
interface Shape2D {
    double area();
}

interface Shape3D extends Shape2D { // A 3D shape has both area and volume
    double volume();
}

class Square implements Shape2D {
    public double area() { return side * side; }
    // Clean! No forced volume method.
}

class Cube implements Shape3D {
    public double area() { /* ... */ return 0.0; }
    public double volume() { /* ... */ return 0.0; }
}
```

## 5️⃣ Dependency Inversion Principle (DIP)
**Definition:** *High-level modules should not depend on low-level modules. Both should depend on abstractions (interfaces). Abstractions should not depend on details; details should depend on abstractions.*

High-level modules (business logic) should not be tightly coupled to low-level modules (database calls, file I/O). Instead, they should interact through interfaces. 
*Quote: "If Open/Closed Principle is the target, Dependency Inversion is the solution."*

### Bad Example (Violating DIP)
A high-level `UserService` directly instantiates and depends on concrete low-level `MySQLDatabase` and `MongoDatabase` classes.

```java
// VIOLATES DIP
class MySQLDatabase {
    public void saveToMySQL(String data) { /* ... */ }
}
class MongoDatabase {
    public void saveToMongo(String data) { /* ... */ }
}

class UserService {
    private MySQLDatabase sqlDb = new MySQLDatabase();
    private MongoDatabase mongoDb = new MongoDatabase();

    // High level module is tightly coupled to concrete implementations
    public void storeUserToSql(String user) { sqlDb.saveToMySQL(user); }
    public void storeUserToMongo(String user) { mongoDb.saveToMongo(user); }
}
```

### Good Example (Following DIP)
Introduce an interface between the high-level and low-level modules. The `UserService` only depends on the `Database` interface.

```java
// FOLLOWS DIP

// The Abstraction
interface Database {
    void save(String data);
}

// Low-level modules depend on the abstraction
class MySQLDatabase implements Database {
    public void save(String data) { /* save logic */ }
}
class MongoDatabase implements Database {
    public void save(String data) { /* save logic */ }
}

// High-level module depends on the abstraction (via Dependency Injection)
class UserService {
    private Database db;

    // The specific database is injected dynamically
    public UserService(Database db) {
        this.db = db;
    }

    public void storeUser(String user) {
        db.save(user); // Doesn't care if it's MySQL or Mongo
    }
}
```

### 💡 Final Note on SOLID
SOLID principles are *guidelines*, not strict laws. In real-world enterprise applications, there are times when you might need to slightly compromise a principle as a trade-off for complex business logic, scalability, or performance requirements. However, you should always strive to adhere to them to keep the codebase clean, extensible, and scalable!
