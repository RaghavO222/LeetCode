# Factory Design Pattern

## 📌 Introduction to the Factory Pattern
In the real world, a factory is a place where products are created. Similarly, in Low-Level Design (LLD), the **Factory Design Pattern** is a creational pattern that provides a centralized class (or method) whose sole responsibility is to create and return objects.

**Why do we need it?** 
In previous patterns like Strategy, we assumed objects (like `new NormalTalk()`) were already instantiated and passed into the client. But who creates these objects? If the client (e.g., your main business logic) creates them using the `new` keyword, the client becomes tightly coupled to the specific concrete classes. 
The Factory Pattern separates the **object creation logic** from the **business logic**.

## 💡 Types of Factory Patterns
The Factory Pattern is generally categorized into three levels of complexity:
1. **Simple Factory (Static Factory)**
2. **Factory Method**
3. **Abstract Factory**

---

## 1️⃣ Simple Factory
A Simple Factory is just a separate class with a method that takes some input (usually an enum or string) and returns the correct object instance. 
* *Note: Simple Factory is not technically an official GoF design pattern, but rather a programming idiom. However, it is highly practical and frequently used.*

### The Problem:
If your `NotificationService` creates `SMSNotification` and `EmailNotification` directly, it violates the **Open/Closed Principle (OCP)** because adding a `PushNotification` requires you to open and modify `NotificationService`.

### Java Implementation: Simple Factory

```java
// 1. The Product Interface
interface Notification {
    void notifyUser();
}

// 2. Concrete Products
class SMSNotification implements Notification {
    public void notifyUser() { System.out.println("Sending SMS..."); }
}
class EmailNotification implements Notification {
    public void notifyUser() { System.out.println("Sending Email..."); }
}

// 3. The Simple Factory
class NotificationFactory {
    // Usually a static method
    public static Notification createNotification(String type) {
        if (type == null) return null;
        if (type.equalsIgnoreCase("SMS")) {
            return new SMSNotification();
        } else if (type.equalsIgnoreCase("EMAIL")) {
            return new EmailNotification();
        }
        throw new IllegalArgumentException("Unknown notification type");
    }
}

// 4. Client Code
public class Client {
    public static void main(String[] args) {
        // The client doesn't use 'new SMSNotification()', it delegates to the factory!
        Notification notification = NotificationFactory.createNotification("SMS");
        notification.notifyUser();
    }
}
```

## 2️⃣ Factory Method Pattern
While the Simple Factory extracts creation logic, it still uses an if-else block. If we add 100 new notification types, the factory class becomes bloated, technically violating OCP internally.

The Factory Method Pattern defines an interface for creating an object, but lets subclasses decide which class to instantiate.

### Java Implementation: Factory Method

```java
// 1. Product Interface and Concrete Products remain the same...

// 2. The Creator (Factory) Interface
abstract class NotificationCreator {
    // The Factory Method
    public abstract Notification createNotification();
    
    // Some business logic that uses the factory method
    public void executeNotification() {
        Notification notification = createNotification();
        notification.notifyUser();
    }
}

// 3. Concrete Creators (Subclasses decide instantiation)
class SMSNotificationCreator extends NotificationCreator {
    @Override
    public Notification createNotification() {
        return new SMSNotification();
    }
}

class EmailNotificationCreator extends NotificationCreator {
    @Override
    public Notification createNotification() {
        return new EmailNotification();
    }
}

// 4. Client Code
public class Client {
    public static void main(String[] args) {
        // We instantiate the specific factory we need
        NotificationCreator creator = new SMSNotificationCreator();
        creator.executeNotification();
    }
}
```

## 3️⃣ Abstract Factory Pattern
The Abstract Factory Pattern works one level higher. It is a factory of factories. It defines an interface for creating families of related or dependent objects without specifying their concrete classes.

### Example Scenario:
Imagine an application supporting a Light Theme and Dark Theme UI. A button and a checkbox in the Light Theme look different from those in the Dark Theme. You need a factory that ensures you get matching components (e.g., a LightButton goes with a LightCheckbox).

### Java Implementation: Abstract Factory

```java
// 1. Abstract Products
interface Button { void render(); }
interface Checkbox { void render(); }

// 2. Concrete Products for Light Theme
class LightButton implements Button { 
    public void render() { System.out.println("Light Button"); } 
}
class LightCheckbox implements Checkbox { 
    public void render() { System.out.println("Light Checkbox"); } 
}

// 3. Concrete Products for Dark Theme
class DarkButton implements Button { 
    public void render() { System.out.println("Dark Button"); } 
}
class DarkCheckbox implements Checkbox { 
    public void render() { System.out.println("Dark Checkbox"); } 
}

// 4. The Abstract Factory Interface
interface GUIFactory {
    Button createButton();
    Checkbox createCheckbox();
}

// 5. Concrete Factories
class LightThemeFactory implements GUIFactory {
    public Button createButton() { return new LightButton(); }
    public Checkbox createCheckbox() { return new LightCheckbox(); }
}

class DarkThemeFactory implements GUIFactory {
    public Button createButton() { return new DarkButton(); }
    public Checkbox createCheckbox() { return new DarkCheckbox(); }
}

// 6. Client Code
public class Application {
    private Button button;
    private Checkbox checkbox;

    // Client accepts ANY factory and gets guaranteed matching elements
    public Application(GUIFactory factory) {
        this.button = factory.createButton();
        this.checkbox = factory.createCheckbox();
    }

    public void paint() {
        button.render();
        checkbox.render();
    }

    public static void main(String[] args) {
        // Switch out the entire family of objects seamlessly!
        GUIFactory lightFactory = new LightThemeFactory();
        Application app = new Application(lightFactory);
        app.paint();
    }
}
```

## 🎯 Factory vs. Strategy: When to use which?
It is common to confuse the Factory pattern with the Strategy pattern. Here is the rule of thumb mentioned in the video:

Strategy: Use this when you want to vary the behavior/algorithm of an object dynamically at runtime (Assuming the object is already created).

Factory: Use this when you want to isolate the creation logic of an object away from the business logic.

Often, these two are combined! A Factory can be used to create the specific Strategy object which is then passed into a context class.
